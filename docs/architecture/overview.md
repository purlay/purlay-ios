# Purlay for iOS — Architecture

Status: foundation built 2026-11-25 (project, package graph, sign-in plumbing, CI). Screens are not.

## 1. Goals and constraints

- **Deployment target iOS 18, built with the iOS 27 SDK (Xcode 27).** Liquid Glass and the iOS 26/27 APIs
  are the primary design; iOS 18–25 get a quiet, system-material fallback behind one availability seam
  (§5), never a second hand-built design.
- **The server's shape is the app's shape.** Purlay is a core plus modules (chat, issues, tasks next;
  project, time and GitHub management later). The app is a core plus feature modules that the server's
  module discovery switches on and off (`API.md` §"Modules"). A module the app does not know is ignored.
- **The contract has one home.** Wire types are generated from the server's contract bundle (D-186,
  D-192) and never written by hand. A contract test runs the client against a real server of the pinned
  version.
- Swift 6.2, strict concurrency, `@Observable`, SwiftUI by default; UIKit only where measured necessary
  (message feed scrolling and the composer's text view are the expected two).

## 2. Package graph

```
                    ┌─────────────── App (composition root) ───────────────┐
                    │  scenes, deep links, APNs, module registry, settings │
                    └───────┬──────────────┬───────────────┬──────────────┘
                            │              │               │
                      FeatureChat    FeatureIssues    Feature… (tasks, time, GitHub)
                            │              │               │
                            └───────┬──────┴───────────────┘
                                    │
                    ┌───────────────┼──────────────────┐
                PurlayModuleAPI  PurlayDesign       PurlayKit  ── PurlayContract (generated)
                (module protocol) (glass, components,  (auth, transport,       PurlayTokens (generated)
                                   availability seam)   realtime, outbox)
```

| Package | Owns | Shared with macOS |
|---|---|---|
| `PurlayContract` | Codable wire types, frames, error codes, generated by `PurlayGen` from the pinned bundle | yes |
| `PurlayTokens` | colour, spacing, type values generated from `packages/tokens` | yes |
| `PurlayKit` | session store (Keychain), transport, handshake, realtime socket with replay, optimistic outbox, uploads, markdown | yes |
| `PurlayModuleAPI` | `FeatureModule` protocol: id, tabs and destinations, search-source renderer, inbox-notice renderer, deep-link routes | iOS only |
| `PurlayDesign` | glass components, haptics, motion, the iOS 18–27 availability seam | iOS only |
| `Feature*` | one server module each: views, view models, local state. Depend on Kit + ModuleAPI + Design, never on each other | iOS only |

Rules: dependencies point down; features never import features (mirrors the server's "modules do not
import one another"); a feature talks to others only through `PurlayModuleAPI` (deep links, inbox
notices, search results). Adding a module = one new `Feature*` package plus one line in the registry.

### Sharing with macOS

`PurlayContract`, `PurlayKit` and `PurlayTokens` (and the `PurlayGen` generator and the contract pin) live in
[`purlay-swift`](https://github.com/purlay/purlay-swift), one package with four products that both Apple apps pin
([ADR 0002](../decisions/0002-shared-swift-packages.md)).

### Repository topology (iOS, macOS, later Android)

```
purlay            server + THE contract (packages/types) -> publishes a versioned contract bundle
purlay-swift      Apple-only shared code: generated Contract, Kit, Tokens   (macOS, iOS, later watchOS/visionOS)
purlay-ios        app + Feature* packages
purlay-macos      app (moves to purlay-swift on its own branch)
purlay-android    app + its own Kotlin core, generated from the SAME bundle
```

- The contract stays in `purlay`: a change to a route and to its type is one atomic commit, and CI there
  already proves the bundle (`contract:bundle --check`). A separate API repo would add a hop where drift
  can happen and nothing it could own that the bundle does not already carry.
- What Android shares is the **bundle**, not Swift code: a Kotlin generator reads the same
  `contract.json`, `tokens.json` and fixtures, and the same live-server contract test runs per client.
- Kotlin Multiplatform for shared logic was rejected: ~36k lines of tested Swift already exist and the
  goal is platform-native feel; a shared runtime would trade that for one more layer.
- Revisit a standalone `purlay-contract` repo only if the bundle needs release artifacts consumed by
  third parties (public SDKs); then publish it from `purlay`'s release, still generated, never hand-edited.

## 3. How the app talks to the server

1. **Handshake.** `GET /api/client` (public) → server version, `contractVersion`, capabilities,
   minimum-client gate. The app refuses to continue against a server it can no longer serve and says why.
2. **Sign-in, no password in the app.** `ASWebAuthenticationSession` opens the server's sign-in page
   (GitHub, Google, OIDC or email link). After the person approves, the page calls
   `POST /api/native/authorize` (PKCE challenge + state) and is redirected to `purlay://auth?code&state`.
   The app calls `POST /api/native/token` with code + verifier + device name and receives the session as
   the `__Host-purlay_session` cookie, which it stores in the Keychain and attaches to every request and
   to the WebSocket upgrade. Sessions are listed and revocable per device (`/api/me/sessions`).
3. **Reads and writes** over HTTP with keyset pagination (`before`/`after`, `nextCursor`); every error is
   `{ error: { code, message } }` and `code` is matched exhaustively from the generated union.
4. **Realtime.** One WebSocket per signed-in session; on reconnect the client replays from its cursors
   (`GET /api/channels/:id/changes` as the HTTP fallback). Sends paint first and reconcile after; a failed
   send shows as failed with retry (the outbox).
5. **Background.** iOS suspends sockets. Closed-app delivery is APNs (§4); on foreground the app replays.
6. **Offline.** A local store (SwiftData or SQLite, decided in the first spike against the replay
   protocol) caches channels and recent messages for cold start under 1.5 s (PRD §5 budget).
7. **Modules.** After sign-in the app reads the server's module list and workspace entitlements and
   builds the tab bar from the registry entries the server has on.
8. **Server address.** Hosted by default; self-hosters enter their own address (HTTPS only in Release,
   local HTTP allowed in Debug).

## 5. Design system and OS-version seam

All version branching lives in `PurlayDesign`, expressed as modifiers (`.purlayGlass(...)`,
`.purlayToolbar(...)`, `.purlayTabBar(...)`). Features never write `#available`.

- iOS 26/27: system Liquid Glass (`glassEffect`, `GlassEffectContainer`, glass button styles, system
  toolbars/tab bars/sheets; iOS 27 toolbar and tab bar APIs). Glass only on the navigation layer, never on
  content.
- iOS 18–25: the same structure with `Material` backgrounds and standard bars.
- Accessibility is part of the seam: Reduce Transparency, Increase Contrast, Reduce Motion, Dynamic Type
  up to AX5, VoiceOver labels on every control, 44 pt targets; checked with `performAccessibilityAudit`.
- Colour, spacing and type come from `PurlayTokens` so iOS and macOS cannot drift.

## 6. Project and tooling

- XcodeGen `project.yml` (as `purlay-macos`), `xcconfig` per configuration, bundle prefix `dev.purlay`,
  languages `en` and `tr`, string catalogs.
- `swift-format` config shared with `purlay-macos` and `purlay-swift` for one style across the apps.
- Tests: Swift Testing for logic; the contract test against a live server of the pinned version;
  XCUITest for sign-in → channel → send; snapshot tests for design components on iOS 18 and 27.
- CI: GitHub Actions on macOS runners: build, unit and contract tests, UI tests on two simulators,
  TestFlight upload on tag.

## 7. Build order

1. **Foundation:** share the three packages, generate contract, project + CI, handshake against a local
   dev server (`bun run dev` seeded demo).
2. **Sign-in:** native PKCE flow end to end, Keychain, device sessions, sign-out.
3. **Shell:** module registry, adaptive navigation (tab bar ↔ sidebar on iPad), workspace switcher.
4. **Chat vertical slice:** channel list, feed, composer, optimistic send, socket + replay, threads.
5. **Inbox, search, profile/settings, Deep Work and quiet hours.**
6. **APNs** (server + app), deep links, widgets and Live Activities only after measured demand.
7. **Issues module**, then each new server module in the same pattern.
